Phase 1: Session Initialization
1
Session Handshake

The phone initiates a DKG session by sending a POST request to the commitment server. This establishes a unique session and exchanges ephemeral public keys for the secure channel. No secrets are exchanged yet -- this is purely a handshake.

Phone (Party 0)
  • public device_pk -- ephemeral ECDH key
  • public curve: secp256k1
  • public protocol: ECDSA-2PC
POST /keygen/init { "curve": "secp256k1", "protocol": "ECDSA-2PC", "device_pk": "04abc...def" }
Server (Party 1)
  • public session_id -- unique identifier
  • public server_pk -- ephemeral ECDH key
  • public capabilities -- supported operations
Response 201 Created { "session_id": "dkg-a1b2c3", "server_pk": "04fed...cba", "capabilities": ["keygen","sign"] }

The server becomes Party 1. No secrets exchanged yet -- just a handshake to establish a secure session. The ephemeral ECDH keys will be used to derive an AES-GCM encryption key for subsequent WebSocket messages. The session_id is used to correlate all future protocol rounds.

Phase 2: Commitment Exchange
2
Mutual Commitment Exchange

Both parties generate cryptographic commitments that bind them to secret choices before revealing anything to the other side. This is the foundation of honest-verifier security -- like sealing your answer in an envelope before the other person reveals theirs.

Phone (Party 0) generates:
  • secret Paillier keypair (N, p, q)
  • secret Random nonce k0
  • public Paillier public key N
  • public Range proof for N
  • public Commitment: H(k0)
// Paillier key generation (N, p, q) = PaillierGen(2048) // Commitment to random nonce com_0 = SHA256(k_0 || r_0) // ZK range proof that N is well-formed pi_N = RangeProof(N, p, q)
Server (Party 1) generates:
  • secret Random scalar t1
  • public EC point T1 = t1 * G
  • public Range proof for T1
  • public Commitment: H(t1)
// Server's random commitment t_1 = random_scalar(secp256k1.n) T_1 = t_1 * G // Commitment to random scalar com_1 = SHA256(t_1 || r_1) // ZK range proof for T_1 pi_T = RangeProof(T_1, t_1)
Commitment Data (both parties now hold)
  • Phone: N (Paillier public key), com_0, range_proof_N
  • Server: T1 (EC point), com_1, range_proof_T

Commitments bind each party to their secret choices before revealing anything. Like sealing your answer in an envelope before the other person reveals theirs. If either party tries to change their secret values after seeing the other's commitment, the hash verification in Phase 3 will fail and the protocol aborts. The Paillier keypair is critical -- it enables the server to perform homomorphic computations on encrypted data in the next phase.

Phase 3: Key Share Computation
3
Encrypted Share Exchange

Each party computes their secret key share contribution and exchanges encrypted data over the secure WebSocket channel. The Paillier encryption scheme allows the server to compute on the phone's encrypted data without ever seeing the plaintext. Both sides verify received data against commitments from Phase 2.

Phone (Party 0) computes:
  • secret x0 -- secret key share
  • public X0 = x0 * G
  • encrypted E(x0) -- Paillier ciphertext
// Generate secret key share x_0 = random_scalar(secp256k1.n) X_0 = x_0 * G // Encrypt for server's homomorphic computation E(x_0) = PaillierEnc(N, x_0) // ZK proof of correct encryption pi_enc = EncProof(x_0, E(x_0), X_0)
Server (Party 1) computes:
  • secret x1 -- secret key share
  • public X1 = x1 * G
  • encrypted E(x1) -- Paillier ciphertext
// Generate secret key share x_1 = random_scalar(secp256k1.n) X_1 = x_1 * G // Encrypt for verification E(x_1) = PaillierEnc(N, x_1) // ZK proof of correct encryption pi_enc = EncProof(x_1, E(x_1), X_1)
Key Variables Summary

Phone holds:

  • secret x0 (private key share)
  • encrypted E(x0) (sent to server)
  • public X0, X1, Q

Server holds:

  • secret x1 (private key share)
  • encrypted E(x1) (sent to phone)
  • public X0, X1, Q

Each party contributes to the key without revealing their contribution. The Paillier encryption allows the server to compute on encrypted data -- this property is essential for later signing operations where the server must help produce a signature without learning the phone's key share. The decommitment values prove the shares are consistent with the commitments from Phase 2.

Phase 4: Key Finalization
4
Joint Public Key Derivation & Storage

Both parties independently compute the joint public key Q from the public EC points exchanged in Phase 3. They then confirm they computed the same result. The full private key x = x0 + x1 never exists on any single device.

Phone (Party 0)
// Compute joint public key Q = X_0 + X_1 = x_0*G + x_1*G = (x_0 + x_1)*G // Verify: matches server's Q assert(Q_phone == Q_server) // Store share in Secure Enclave SecureEnclave.store(x_0, tag: key_id)
  • secret x0 -- stored in Secure Enclave
  • public Q -- joint public key (displayed)
Server (Party 1)
// Compute joint public key Q = X_0 + X_1 = x_0*G + x_1*G = (x_0 + x_1)*G // Verify: matches phone's Q assert(Q_server == Q_phone) // Store share in encrypted KV/SQLite EncryptedDB.store(x_1, session_id)
  • secret x1 -- stored in encrypted KV
  • public Q -- joint public key (stored)
Qphone == Qserver

Both parties independently derived the same joint public key.

The Ethereum address is derived: addr = keccak256(Q.x || Q.y)[12:]

Public (known to both + world)

  • Q -- joint public key (compressed SEC1, 33 bytes)
  • X0 -- Phone's public share
  • X1 -- Server's public share
  • N -- Paillier public modulus
  • Ethereum address derived from Q

Secret (never leaves its device)

  • x0 -- Phone's private share (Secure Enclave)
  • x1 -- Server's private share (encrypted KV)
  • (p, q) -- Paillier primes (Phone only)
  • x = x0 + x1 -- NEVER computed anywhere

The full private key x = x0 + x1 NEVER exists on any single device. Neither the phone nor the server alone can sign a transaction. Both must cooperate in a 2-party signing protocol to produce a valid ECDSA signature. This is the core security property of threshold cryptography.

Phase 5: Failure Modes
5
Failure Modes & Recovery

The DKG protocol is designed to fail safely. At every stage, if something goes wrong, both parties abort cleanly without leaking partial secrets. The protocol guarantees: either both parties get valid key shares, or neither does.

Failure Mode Detection Recovery
Timeout (30s) Any protocol round exceeds 30-second deadline. Timer runs independently on both parties. Both parties abort immediately. No partial state persisted. Phone shows "Session Expired" alert. Must restart with new session.
Invalid Commitment Range proof verification fails, or decommitment doesn't match hash from Phase 2. Caught by assert(H(val || r) == com). Protocol aborts immediately. Bad actor is identified (the party whose proof/commitment failed). Session is logged as suspicious. No retry -- user must investigate.
Network Drop WebSocket closes unexpectedly. Server detects via heartbeat (ping/pong every 5s). Phone detects via URLSessionWebSocketTask delegate. Session can resume from last completed round (rounds are idempotent). Both sides persist round state. After 5 minutes without reconnection, session expires and all state is wiped.
Server Crash Phone receives WebSocket disconnect or HTTP 502/503 from load balancer. No heartbeat response within 10s. Phone retries with exponential backoff (1s, 2s, 4s). Can start new session -- old session's partial state is cleaned up by server's garbage collector (runs every 60s).
Invalid ZK Proof Paillier range proof or encryption proof fails verification. The verifier's VerifyProof() returns false. Protocol aborts. The party with the invalid proof is flagged. This could indicate a malicious party attempting to bias the key generation. All state is destroyed.
Duplicate Session Phone attempts to init a new DKG while an existing session is active for the same device_pk. Server rejects with 409 Conflict. Phone must either resume the existing session or explicitly cancel it before starting a new one.
Protocol Invariant: For any failure at round R: - Secrets generated in rounds 0..R-1 are safe (committed + verified) - Round R's data is discarded (not committed) - No partial private key material leaks - Both parties can independently verify the abort was legitimate

All-or-nothing guarantee: Either the full DKG completes successfully and both parties hold valid key shares, or the protocol aborts cleanly with zero information leakage. There is no partial success state.
