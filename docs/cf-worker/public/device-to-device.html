Discovery & Connection
1
Peer Discovery (MultipeerConnectivity)

Each device broadcasts its presence on the local network using Apple's MultipeerConnectivity framework with Bonjour service type _cbmpc._tcp. Bluetooth LE handles initial discovery; WiFi Direct takes over for high-bandwidth protocol messages.

What's exchanged during discovery:

  • public Device name (user-visible label)
  • public Capabilities: curves supported (secp256k1, ed25519), max party count
  • public Session nonce (random 32 bytes, prevents replay)

Apple's MultipeerConnectivity uses Bluetooth LE for initial discovery, then upgrades to WiFi Direct for high-bandwidth protocol messages. The framework handles NAT traversal, encryption of the transport layer, and reconnection automatically.

2
Mutual Authentication & Role Assignment

Devices exchange ephemeral ECDH keys to establish an encrypted channel, then the user confirms pairing on each device. Party indices are assigned deterministically — no central coordinator required.

Role assignment (deterministic, no coordinator): sorted_keys = sort([PK_A, PK_B, ...]) // lexicographic party_index[device] = sorted_keys.indexOf(device.PK) Example: PK_A = 02a1... < PK_B = 03d4... → Device A = Party 0 → Device B = Party 1

No trusted third party needed. Roles are deterministic — the device with the "smaller" public key becomes Party 0. This eliminates race conditions and ensures all devices agree on the same assignment without coordination.

3
QR Pairing Fallback

When devices are not on the same local network — different WiFi networks, cellular only, or Bluetooth out of range — QR code pairing provides a fallback path. Device A generates a QR code containing session metadata and its public key. Device B scans it and connects through a relay server.

QR data structure:

{ "sessionId": "a7f3b2c1-...", "relayURL": "wss://relay.cbmpc.dev/v1", "devicePK": "02a1b2c3d4e5f6a7b8c9...", "curve": "secp256k1", "protocol": "ecdsa-2pc", "version": 1 }

The relay server is a dumb pipe — all it does is forward bytes between two session IDs. Messages are E2E encrypted with the device keys exchanged via QR. Even if the relay is compromised, an attacker sees only ciphertext. The QR code bootstraps trust: Device B knows Device A's public key from scanning, and Device A authenticates Device B via an ECDH handshake over the relay.

2-Party DKG over Peer Channel

Same ECDSA-2PC protocol as the server-backed DKG ceremony, but messages travel over MultipeerConnectivity (or the QR relay) instead of WebSocket to a central server. The cryptography is identical — only the transport changes.

  • secret share_A — Device A's key share
  • secret Paillier secret key (Device A)
  • secret share_B — Device B's key share
  • secret Paillier secret key (Device B)

Identical cryptography to the server-backed flow — only the transport changes. Your key share never leaves your device. Each share is stored in the Secure Enclave (or the iOS Keychain with biometric protection), meaning even a device backup won't expose the raw key material.

5
N-Party DKG (3+ Devices)

For threshold setups with 3 or more devices, the protocol uses Feldman VSS — each device generates a random polynomial, publishes commitments, and privately whispers shares to every other device. See the Threshold Signing guide for the full Feldman VSS math.

Message count grows quadratically. For 3 devices this is fine over MultipeerConnectivity. Beyond 5 devices, consider a star topology with a coordinator device that relays messages — reducing each device's connections from N-1 to 1, at the cost of trusting the coordinator with message routing (but not with secrets).

6
Collaborative Signing

Device A has a message or transaction to sign. It broadcasts a signing request to all connected peers. Only the required threshold of devices need to participate — for a 2-of-3 setup, any two devices can complete the signature while the third stays offline.

Device A [1/3] Nonce commitment ........... [DONE] [2/3] Partial signature .......... [DONE] [3/3] Assembly ................... [DONE] Signature: (R, s) = 0x3045...
Device B [1/3] Nonce commitment ........... [DONE] [2/3] Partial signature .......... [DONE] [3/3] Assembly ................... [DONE] Signature verified locally

Any 2-of-3 devices can sign. The third device can be offline. The resulting signature is indistinguishable from a single-signer signature — a blockchain verifier has no way to know that two separate devices collaborated to produce it.

7
Audit & Verification

All participating devices log the signing event. Any device — or any external verifier — can verify the resulting signature using standard ECDSA verification. No MPC knowledge is required.

Signing Event Log (each device stores)

timestamp: 2025-01-15T14:23:07Z msg_hash: 0x7f83b1657ff1fc... parties: [Device A, Device B] threshold: 2-of-3 signature: 0x3045022100... pubkey: 02a1b2c3d4e5f6...

Verification Equation

ECDSA verification: ECDSA_verify(Q, message, (r, s)) u1 = hash(msg) * s^(-1) mod n u2 = r * s^(-1) mod n R' = u1*G + u2*Q valid = (R'.x mod n) == r
SIGNATURE VALID

Standard ECDSA signature. Any wallet, blockchain node, or openssl can verify it.
The multi-device origin is invisible in the output.

Every device keeps an immutable audit log. The signature is a standard ECDSA signature — any wallet or blockchain can verify it. There is no way for a verifier to distinguish it from a signature produced by a single key on a single device.
